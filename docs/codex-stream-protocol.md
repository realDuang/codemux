# Codex stream protocol and compatibility

CodeMux's two Codex engines share conversation concepts, but use different wire
protocols. The normal engine consumes public app-server events. The shared
Desktop engine follows an execution owner's private, versioned conversation
state. Preserve this boundary: normalize both in the adapters, then render the
same unified message types without engine-specific frontend branches.

The implemented baseline is standalone CLI **0.162.1** and the inspected Desktop
build below. The conversation UI plan has been implemented, including native
activity grouping, session-scoped images, history disclosure, and asynchronous
questions. See [the follow-up delivery](#cli-upgrade-and-display-completion) for
the earlier runtime/browser checkpoint, [the UI plan](codex-ui-parity-plan.md)
for the approved display scope, and the final sections for subsequent fixes.

## Two transports, one normalized conversation model

| Concern | Public app-server | Private Desktop coordination |
| --- | --- | --- |
| Transport used by CodeMux | Newline-delimited JSON over a child process's stdin/stdout | Local socket or Windows named pipe; four-byte little-endian length followed by JSON |
| Envelope | Request `{id, method, params}`, response `{id, result/error}`, notification `{method, params}` | Typed `request`, `response`, and `broadcast` envelopes with method versions and client routing |
| Initialization | One `initialize` request, then `initialized`, per connection | Private `initialize` request returns a router `clientId` |
| Conversation identity | `threadId`, `turnId`, `itemId` | `hostId`, `conversationId`, owner client, local turn identity, and native `turnId` |
| Incremental updates | `turn/*`, `item/*`, indexed reasoning and text/output deltas | `thread-stream-state-changed` **method version 11**: snapshots or revisioned state patches |
| Sending input | `turn/start`, `turn/steer`, `turn/interrupt` | Versioned `thread-follower-*` requests routed to the discovered owner |
| Recovery | Resume the same native thread and hydrate its history | Rediscover the owner, re-follow, and obtain a new authoritative snapshot |

Version 11 belongs to one Desktop method; it is not a global app-server protocol
version. Exporting the Desktop binary's app-server types does not export this
private IPC schema. Sharing a provider URL or rollout directory also does not
make two processes live followers of the same execution owner.

[`jsonrpc-client.ts`](../electron/main/engines/codex/jsonrpc-client.ts),
[`index.ts`](../electron/main/engines/codex/index.ts),
[`converters.ts`](../electron/main/engines/codex/converters.ts),

## Public stream contract

The following is a minimal lifecycle sketch, not a captured transcript or a
complete list of notifications. Request acknowledgements can interleave with
notifications; clients must correlate IDs instead of assuming one fixed order.

```text
client -> initialize(id=1, clientInfo, capabilities)
server -> response(id=1)
client -> initialized
client -> thread/start or thread/resume(id=2)
server -> response(id=2, thread.id=T)
client -> turn/start(id=3, threadId=T, input)
server -> response(id=3, turn.id=U)
server -> turn/started(threadId=T, turn.id=U, status=inProgress)
server -> item/started(threadId=T, turnId=U, item.id=A)
server -> item/agentMessage/delta(T, U, A, delta) [zero or more]
server -> item/completed(T, U, item.id=A, final item)
server -> [more reasoning, commentary, tool, or answer item lifecycles]
server -> turn/completed(threadId=T, turn.id=U, terminal status)
```

### Identity, order, and phase

- Keep thread, turn, item, and JSON-RPC request IDs distinct. Scope UI keys by
  conversation and turn; do not assume native item IDs are globally unique.
  Replaying the same history must produce the same message and part identities.
- One turn can contain several `agentMessage` items around tools. Preserve their
  individual IDs and order. `commentary -> commandExecution -> final_answer`
  must remain three ordered units after streaming, hydration, and reconnect.
  Concatenating all text into one turn-wide buffer loses both position and phase.
- `agentMessage.phase` is `commentary | final_answer | null` in CLI 0.154.0.
  Desktop's bundled version adds `partial_answer`: stable answer text that may
  be followed by further output or tools. A missing/null phase is unknown, not
  evidence of a final answer. Preserve unknown-phase compatibility.
- A final-answer item does not by itself close the turn. The turn lifecycle
  controls completion. Expanded compact turns preserve commentary, partial
  answers, tools, and final answers in their original order. The outer steps
  disclosure hides all non-final output together; every visible final fragment
  remains outside it. Item completion alone does not make an item a final answer.

Relevant generated files: `MessagePhase.ts`, `v2/ThreadItem.ts`,
`v2/AgentMessageDeltaNotification.ts`, `v2/ItemStartedNotification.ts`, and
`v2/ItemCompletedNotification.ts`.

### Deltas and authoritative completion

| Notification | Accumulation key | Meaning |
| --- | --- | --- |
| `item/agentMessage/delta` | `(threadId, turnId, itemId)` | Append `delta` to that message item |
| `item/plan/delta` | Same item tuple | Provisional plan text; final plan may differ |
| `item/reasoning/summaryTextDelta` | Item tuple plus `summaryIndex` | Append within one readable summary section |
| `item/reasoning/summaryPartAdded` | Item tuple plus `summaryIndex` | Section boundary, not an independent reasoning card |
| `item/reasoning/textDelta` | Item tuple plus `contentIndex` | Append within one available reasoning content block |
| `item/commandExecution/outputDelta` | Item tuple | Ordered stdout/stderr output |
| `item/completed` | `item.id` within thread and turn | Authoritative final item, not another text delta |

Keep one stable reasoning part per native reasoning item. Empty sections and
unavailable/encrypted content must not create empty cards. Summary/content
indices are separate namespaces. Only `summary` is selected for the visible
reasoning display; do not append or fall back to raw `content`. Preserve summary
section order and repeated sections. Ignore late deltas after an item or turn
has closed.

Apply the completed item's supplied text/output/state as a replacement, without
appending it again to the streamed value. Preserve richer live data when reading
an explicitly partial history representation. `turn.items` is not automatically
a full transcript: inspect `itemsView` (`notLoaded`, `summary`, or `full`) and use
item events or pagination for missing data.

The tool is running until its item state or lifecycle says otherwise. Hydrating
an `inProgress` turn must not complete its tool parts. Turn `startedAt` and
`completedAt` use seconds; item lifecycle `startedAtMs` and `completedAtMs`, and
tool `durationMs`, use milliseconds. Convert once and retain native timing where
available instead of replacing it with the history-read time.

### Retry, interruption, and recovery

- `error` carries `threadId`, `turnId`, `error`, and `willRetry`. A recoverable
  error with `willRetry: true` does not close the turn or release queued input.
  Terminal `turn.status` is `completed`, `interrupted`, or `failed`.
- Do not let a delayed acknowledgement, old-turn error, or late completion
  overwrite a newer active turn. Correlate every mutation with its native turn.
  Cancellation response and interrupted completion may arrive in either order;
  finish the same turn only once.
- `turn/steer` requires `expectedTurnId` and does not create a new turn.
  `turn/interrupt` requires the target `threadId` and `turnId`.
- `thread/read` reads stored state; `thread/resume` joins or loads a live thread.
  Prefer resumption by native `threadId`. Never substitute a new thread when
  restoration fails. `thread.sessionId` identifies a session tree and can differ
  from the thread ID.
- Paginated history is a separate contract. Resume with `excludeTurns: true`
  when supported, then use `thread/turns/list` and `thread/items/list`, retaining
  opaque cursors. An absent page is unknown history, not a deleted item. Merge
  fetched history and ongoing events by native identity rather than arrival time.

Relevant generated files: `v2/ErrorNotification.ts`, `v2/Turn.ts`,
`v2/TurnStatus.ts`, `v2/TurnSteerParams.ts`, `v2/TurnInterruptParams.ts`,
`v2/ThreadResumeParams.ts`, `v2/ThreadResumeResponse.ts`, and pagination types.

### Approvals and questions

Approvals are server-initiated **requests**, not ordinary notifications. Reply
with the original JSON-RPC `id`, preserving its string/number type. Keep pending
state scoped to thread, turn, and request; `itemId` alone cannot identify every
approval callback. Command requests can additionally carry an `approvalId`.

- `item/commandExecution/requestApproval`: honor `availableDecisions` and any
  network context. Decisions can be strings or structured policy amendments.
- `item/fileChange/requestApproval`: use its own decision contract.
- `item/permissions/requestApproval` and `mcpServer/elicitation/request` have
  distinct payload/response schemas; do not coerce them into command approval.
- `item/tool/requestUserInput`: preserve questions and the `isBlocking` flag;
  the deprecated `autoResolutionMs` field does not determine blocking.
- `serverRequest/resolved` identifies the request to clear. Resolution and tool
  completion are separate transitions; a dismissed prompt is not proof that the
  tool succeeded.

Use `ServerRequest.ts` and the corresponding `v2/*Params.ts` / `*Response.ts`
from the selected binary. Do not broaden an approval while normalizing it.

## Desktop state contract

The router assigns a client ID. Discover the owner for `(hostId, conversationId)`,
then announce following to that owner. Accept only correctly versioned messages
from the expected owner and responses handled by the intended client. Start,
steer, interrupt, settings, and approval commands remain owner-routed operations.
The current local method versions are recorded in `DESKTOP_IPC_VERSIONS`; each
must be rechecked after a Desktop upgrade.

The essential envelopes are:

```text
request:   {type: "request", requestId, sourceClientId, method, version,
            params, targetClientId?, timeoutMs?}
response:  {type: "response", requestId, method, resultType: "success" | "error",
            handledByClientId?, result?, error?}
broadcast: {type: "broadcast", sourceClientId, method, version,
            targetClientIds?, params}
```

Owner discovery uses method version 1. Following uses
`thread-stream-following-changed` version 1; state broadcasts use version 11.
Local start/steer/interrupt use versions 2/1/4 respectively. Router discovery and
request completion have separate time budgets: a timeout does not prove that an
input was never delivered, so reconcile state before retrying a write.

The owner broadcasts one of these `change` shapes:

```text
snapshot: {type, revision, conversationState}
patches:  {type, baseRevision, revision, patches, acceptedTextChanges?}
```

Patches use Immer-style `add`, `replace`, and `remove` with array paths. They are
state edits, not app-server deltas and not JSON Pointer strings. Apply them in
order only when `baseRevision` equals the accepted revision and the new revision
advances. Reject a malformed update without changing the last good state; a gap
requires resynchronization. Array insertion/removal shifts subsequent indices.
Do not append `acceptedTextChanges` to already patched text: it is a transcript
reader optimization accompanying the authoritative state edits.

Desktop's canonical `turnHistory` and legacy/live `turns` can coexist. Reconcile
their turn/item identities while retaining richer live timing, completion, and
request state. Local turn IDs and native `turnId` serve different purposes;
preserve both until the owner confirms submission. A pending submission is not
a new completed turn. Reconnect must replace an obsolete owner/revision epoch,
not replay old patches onto a new snapshot.

Detailed usage and isolated runtime probes are documented in
[Shared Codex Desktop conversations](codex-desktop-sharing.md). Historical
acceptance recorded there applies to its stated build and scenarios; it is not
fresh acceptance of subsequent stream changes.

## Where REA helps

REA can statically inspect ASAR/JavaScript, trace literal IPC channels and call
relationships, and compare application versions without executing the target.
It is useful when bundle wrappers make direct string/AST inspection difficult.
Dynamic channels and ambiguous handlers remain unknown; a static edge does not
prove execution order. A one-off pinned CLI analysis does not require global
agent setup or a native decompiler.

REA cannot alone produce replayable Codex protocol captures. Its
[active Electron hook](https://github.com/morluto/rea/blob/58300885207133422af235e0f2b10658cf958b03/scripts/electron-active-hook.cjs#L35)
retains only coarse value kinds such as `object` and `string`, not IPC object
fields or payload values. Its
[passive Inspector provider](https://github.com/morluto/rea/blob/58300885207133422af235e0f2b10658cf958b03/docs/javascript-runtime-observation.md#L86)
observes scripts/contexts, not IPC messages. Active scenarios launch a separate
instrumented application and can change its external-effect behavior. This audit
read REA's source; it did not install or execute REA against Desktop.

## Observed live event sequence

A bounded ephemeral thread was exercised through the Desktop-bundled
`0.162.0-alpha.17.2` binary, with a temporary working directory and one stdout-only
command. It completed in 9.55 seconds without a turn error or retry. The observed
sequence was:

```text
turn/started
  userMessage: item/started -> item/completed (same item ID)
  agentMessage(commentary): item/started -> text deltas -> item/completed
  commandExecution: item/started -> item/completed
  reasoning: item/started -> item/completed (empty readable summary/content)
  agentMessage(final_answer): item/started -> text deltas -> item/completed
turn/completed
```

The final notification's `turn.items` contained only the final answer item. It was
not a complete transcript and must not replace accumulated live items. This also
confirms that `item/completed` for `userMessage` must not create a tool card.
Empty reasoning was an observed protocol item, not evidence of missing readable
content.

The system `0.154.0` binary was tested once with the same bounded scenario. It
emitted turn start and the user item's complete lifecycle, then produced no
assistant items before the 110-second timeout. That run does **not** establish a
successful end-to-end CLI result or a root cause for the timeout. Neither probe
connected to an existing Desktop conversation.

## Acceptance boundaries

Protocol inspection establishes the contracts above. Regression tests should
assert observable behavior for: ordered commentary/tool/answer items; stable
replay IDs; indexed reasoning; authoritative completion; running-tool history;
retry followed by success; late old-turn events; cancellation races; pending
request resolution; Desktop patch gaps; and reconnect with the same native IDs.

These adapter tests are necessary but do not establish native UI parity. Fresh
acceptance also needs dedicated conversations on each transport, captured event
sequences, history/reconnect comparison, and screenshot/input checks of the
rendered result. Cross-client sharing, every approval variant, unknown item types,
and newer Desktop versions remain unverified unless a specific result records
the version, scenario, and outcome. Keep completion reports explicit about which
checks actually ran; do not inherit a previous release's live acceptance.


## Native activity grouping and session image previews (2026-10-14)

This increment follows the installed Codex Desktop 26.1007.30912 (20156), whose
ASAR SHA-256 remains `75e397e2280dde93b70a85aa926f4282c728eacc84dfeb15ba7fb6ddd84628af`.
This grouping was first gated by a `compactActivityGroups` capability enabled
only by the two Codex adapters. It is now the single renderer path for every
engine: the capability, the legacy turn-level steps container and ContextGroup
were removed, and the gateway derives `displayActions` for engines that do not
supply them (see "Engine-agnostic activity timeline" in
[design-system.md](design-system.md)).

### Verified grouping rules

- Every assistant text item, including commentary, ends the preceding activity
  slice in the expanded chronology. This boundary does not exempt commentary
  or partial answers from the turn's outer steps disclosure.
- Ordinary reasoning stays in its activity slice and does not split adjacent
  tools. Explicit standalone notices and subagent activity end a tool group.
- One `commandExecution.commandActions` array can become several display rows.
  CodeMux retains one ToolPart execution identity and adds `displayActions`;
  started, completed and history conversion share the same normalization.
- Completed singleton commands use plain rows; running or multi-action groups
  retain a group header. Raw input/output, partial error output and diffs remain
  available through lazy details. Shell metadata output remains a supported fallback.
- Header categories follow a fixed order. Recognized skill-definition reads
  contribute to Loaded tools; ordinary read/search/list actions contribute to
  Read files; other commands contribute to Ran commands. Arbitrary files named
  SKILL.md are not classified as loaded tools.
- Activity icons use a 0.875 rem slot plus a 0.375 rem gap. Group contents have no
  net extra left indentation, and the expanded viewport is capped at 14 rem.

Source pointers use JavaScript UTF-16 offsets in the assets already recorded in
[codex-ui-parity-plan.md](codex-ui-parity-plan.md): G:N@695, G:F@1213,
F:F@6354, F:ke@7764, F:Pe@12624, F:Ye@20704, I:dr@20282,
S:NO@339243, H:FI@359349 and H:BJe@359921. In these pointers, I is
`agent-activity-item-40fa48e24fdc.js` (SHA-256
`2033a57b392897e437ab29d004320a22cabcd6c81613c9e89ff3978c96b7a1f3`).
The installed grouping assets were compared byte-for-byte with the extracted
reference. No official application code was copied into CodeMux.

## History disclosure and asynchronous questions (2026-10-15)

Historical `stepCount` metadata and the local `stepsLoaded` cache serve different
purposes. Loading steps must not remove their disclosure control. Compact turns
retain the outer steps control while process content exists or steps remain
unloaded, including live and fully loaded turns without `stepCount`. Internal
events alone do not leave an empty disclosure after loading.

Collapsing outer steps hides all non-final output: commentary, partial answers,
reasoning, tools, notices, and standalone tool attachments. The user prompt and
every visible final-answer fragment remain, including each fragment's inline
assets and source notes. Expanding restores the original chronology; nested tool
details retain their own disclosure state. Pending input controls and terminal
error/status UI remain available through their existing surfaces.

An active compact turn defaults to expanded and a finished turn defaults to
collapsed. An explicit user choice overrides both defaults and persists across
the active-to-complete transition. A completed commentary or partial-answer item
stays process output. If no final phase exists, only the last visible unphased
text in a successfully finished turn uses the legacy answer fallback; active,
failed, or interrupted turns do not promote it. No-final turns keep their
process content available through steps. OpenCode, Copilot, and Claude retain
their existing renderer and unphased response behavior.

Use the opt-in [`folding-stream` fixture](../tests/fixtures/ui-parity/README.md#compact-turn-folding-stream)
to check process text before tools, item completion, manual disclosure choices,
and the transition to the final streamed answer without lazy-step metadata.

Asynchronous questions arrive in `agentMessage.questions`, separately from the
blocking `item/tool/requestUserInput` request. Each native question ID is
`JSON.stringify(["request_user_input_async", item.id, questionIndex])`. The adapters
preserve original titles and option labels, expose the existing `UnifiedQuestion`
contract, and scope pending groups to the native thread and active turn.

Replies use a complete `send_user_message_question_reply` envelope containing
question IDs, original questions, and trimmed answers. Desktop routes this through
`thread-follower-steer-turn` with the async-question restoration context. CLI uses
`turn/steer` with the expected active turn; a failed reply cannot become a queued
prompt or start another turn. Partial answers leave the remaining questions
pending. Pending or failed steering does not count as an accepted answer.

CodeMux-owned Desktop threads also validate the async marker and question IDs at
the refreshed owner boundary before sending a turn-bound request. The inspected
official Desktop v1 follower method does not accept a caller's expected turn ID;
its native implementation may retry a turn mismatch against the current turn.
The official-owner path therefore has the same local precheck limitation as the
native UI and cannot promise atomic original-turn targeting through this IPC.

Only receipt batches whose IDs all match questions from the same turn are
normalized into assistant question/answer history. Unknown, mixed, quoted, or
malformed examples stay ordinary user content. Dismissing an async question is
local display state and sends neither an empty answer nor a turn interruption.
Blocking questions and permission requests retain their separate reply contracts.
Answer receipts use a text-only conversion path and cannot authorize the
assistant-only visualization-file resolver.

The gateway restores reply routes after failed submissions and when pending
requests are recovered, while protecting in-flight submissions against duplicate
answers. Compact conversations use the existing input-area controls without a
second unstyled prompt in the transcript. The other rendering branches are
unchanged.

Regression coverage includes active/terminal turns, accepted steering, partial
answers, stale snapshots, local dismissal, literal receipt examples, retry routes,
and cross-session identity. Browser fixtures exercise options, free text, pending
recovery, and allow/deny controls without executing a command. Feishu mock tests
exercise the existing exact-label and custom-text answer paths; they do not claim
new numeric shortcuts, multi-question collection, or manual permission approval
support in that channel.
